# Synthetic Dataset JSON Schema Reference

This document is the authoritative reference for the Azure AD tenant snapshot format
consumed by the RBAC Policy Auditor.  Every dataset uploaded via `POST /api/v1/datasets`
or generated by `scripts/generate_synthetic_data.py` must conform to this schema.

The canonical Pydantic model definitions live in
[`app/schemas/dataset_schema.py`](../app/schemas/dataset_schema.py).
This document exists to make the schema accessible without reading Python source.

## Top-Level Structure

A dataset payload is a JSON object with **four required top-level keys**, each
containing an array.  Empty arrays are valid but will produce no audit findings.

```json
{
  "users": [ /* UserRecord[] */ ],
  "roleAssignments": [ /* RoleAssignmentRecord[] */ ],
  "signInLogs": [ /* SignInLogRecord[] */ ],
  "groups": [ /* GroupRecord[] */ ]
}
```

| Key | Type | Required | Description |
|-----|------|----------|-------------|
| `users` | `UserRecord[]` | Yes | All principals in scope for this snapshot |
| `roleAssignments` | `RoleAssignmentRecord[]` | Yes | All active directory role assignments at snapshot time |
| `signInLogs` | `SignInLogRecord[]` | Yes | Interactive sign-in events for the observation window (up to 90 days) |
| `groups` | `GroupRecord[]` | Yes | Security and role-assignable groups in the tenant |

---

## users[]

Each element represents a single principal: a human user, a B2B guest, or a
service principal (managed identity or application identity).

### Schema

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `id` | `string` (UUID) | Yes | Azure AD object ID.  Primary join key across all arrays. |
| `displayName` | `string` | Yes | Human-readable name shown in the Azure portal. |
| `userPrincipalName` | `string` | Yes | UPN (`user@domain.com`) or application identifier URI for service principals. |
| `userType` | `"Member" \| "Guest" \| "ServicePrincipal"` | Yes | Principal category. |
| `accountEnabled` | `boolean` | Yes | `true` when the account is active; `false` when disabled. |

### userType Values

| Value | Meaning |
|-------|---------|
| `Member` | Internal employee or cloud-only account |
| `Guest` | B2B guest invited from an external tenant |
| `ServicePrincipal` | Application identity, managed identity, or service account |

### Example

```json
{
  "id": "11111111-1111-1111-1111-111111111111",
  "displayName": "Alice Johnson",
  "userPrincipalName": "alice.johnson@contoso.onmicrosoft.com",
  "userType": "Member",
  "accountEnabled": true
}
```

## roleAssignments[]

Each element records a single active directory role assignment at snapshot time.
A user who holds three roles appears in three separate entries.  Group-inherited
roles also appear here — one entry per (principal, role) pair — with
`assignmentType` set to `"group"` and `assignedVia` naming the group.

### Schema

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `id` | `string` | Yes | Unique identifier for this assignment record (UUID or synthetic ID). |
| `principalId` | `string` (UUID) | Yes | Object ID of the principal that holds the role.  Must match a `users[].id` or `groups[].id`. |
| `roleDefinitionId` | `string` (UUID) | Yes | Immutable Azure AD role definition ID.  Use real built-in GUIDs where possible. |
| `roleName` | `string` | Yes | Human-readable role display name, e.g. `"Global Administrator"`. |
| `assignmentType` | `"direct" \| "group"` | Yes | How the role is held. |
| `assignedVia` | `string \| null` | No | Display name of the group through which the role is inherited.  Must be non-null when `assignmentType == "group"`. |
| `assignedAt` | `string` (ISO 8601) | Yes | UTC timestamp when the assignment was created. |

### assignmentType Values

| Value | Meaning |
|-------|---------|
| `direct` | Role is assigned directly to the principal via the Roles and Administrators blade |
| `group` | Role is inherited because the principal is a member of a role-assignable group |

### Example — Direct Assignment

```json
{
  "id": "ra-direct-001",
  "principalId": "11111111-1111-1111-1111-111111111111",
  "roleDefinitionId": "62e90394-69f5-4237-9190-012177145e10",
  "roleName": "Global Administrator",
  "assignmentType": "direct",
  "assignedVia": null,
  "assignedAt": "2023-03-10T09:00:00Z"
}
```

### Example — Group-Inherited Assignment

```json
{
  "id": "ra-group-042",
  "principalId": "22222222-2222-2222-2222-222222222222",
  "roleDefinitionId": "fe930be7-5e62-47db-91af-98c3a49a38b1",
  "roleName": "Privileged Role Administrator",
  "assignmentType": "group",
  "assignedVia": "Tier0-Admins (PIM)",
  "assignedAt": "2022-11-01T14:30:00Z"
}
```

## signInLogs[]

Each element records a single interactive sign-in event.  The pipeline uses
this array to determine the most recent sign-in timestamp per principal,
which drives dormancy detection.

Multiple entries per user are expected — one per sign-in event.  A user with
no entries in this array is treated as having **never signed in**, which is
itself a high-signal dormancy indicator.

### Schema

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `id` | `string` | Yes | Unique identifier for this log entry. |
| `userId` | `string` (UUID) | Yes | Object ID of the signing-in user.  Must match a `users[].id`. |
| `userDisplayName` | `string` | Yes | Display name at the time of the event (denormalised for readability). |
| `signInTimestamp` | `string` (ISO 8601) | Yes | UTC timestamp of the sign-in event. |
| `appDisplayName` | `string` | Yes | Application the user authenticated against. |
| `status` | `"Success" \| "Failure"` | Yes | Outcome of the sign-in attempt. |
| `ipAddress` | `string` | Yes | Source IP address.  Use RFC 5737 documentation addresses (e.g. `203.0.113.x`) in synthetic data. |

### Typical appDisplayName Values

These values mirror what Azure AD Sign-in logs actually report:

- `"Microsoft Azure Management"` — Azure portal / ARM API access
- `"Microsoft Teams"` — Teams desktop or web client
- `"Office 365 Exchange Online"` — Exchange / Outlook access
- `"Microsoft Office"` — Office desktop apps
- `"Windows Sign In"` — Hybrid Azure AD join sign-in
- `"Microsoft Graph"` — Direct Graph API calls (common for service principals)
- `"Azure Active Directory PowerShell"` — PowerShell / admin tooling

### Example

```json
{
  "id": "sl-20241105-001",
  "userId": "11111111-1111-1111-1111-111111111111",
  "userDisplayName": "Alice Johnson",
  "signInTimestamp": "2024-11-05T09:12:00Z",
  "appDisplayName": "Microsoft Azure Management",
  "status": "Success",
  "ipAddress": "203.0.113.42"
}
```

## groups[]

Each element represents a security or role-assignable group.  Groups are the
mechanism for inherited role assignments.  Every member of a group that holds
a directory role inherits that role, which must be reflected in
`roleAssignments[]` with `assignmentType: "group"`.

### Schema

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `id` | `string` (UUID) | Yes | Azure AD object ID of the group. |
| `displayName` | `string` | Yes | Human-readable group name. |
| `isRoleAssignable` | `boolean` | No (default `false`) | `true` when the group was created with the `isAssignableToRole` flag, enabling it to hold directory roles. |
| `members` | `string[]` | No (default `[]`) | Array of `users[].id` values for direct members of this group. |
| `assignedRoles` | `string[]` | No (default `[]`) | Array of `roleDefinitionId` values for roles assigned to this group. |

> **Note on membership flattening:** Nested group membership (a group whose
> member is another group) is pre-flattened in the synthetic dataset.  Each
> user's effective group membership is expanded at generation time so the
> pipeline does not need to recurse through group hierarchies.

### Example

```json
{
  "id": "aaaaaaaa-aaaa-aaaa-aaaa-aaaaaaaaaaaa",
  "displayName": "Tier0-Admins (PIM)",
  "isRoleAssignable": true,
  "members": [
    "22222222-2222-2222-2222-222222222222",
    "33333333-3333-3333-3333-333333333333"
  ],
  "assignedRoles": [
    "fe930be7-5e62-47db-91af-98c3a49a38b1"
  ]
}
```

## Cross-Reference Invariants

The ingestion service enforces the following consistency rules (FR-2).  Violations
are returned as structured 422 errors.

1. **Principal references:** Every `roleAssignments[].principalId` must match
   either a `users[].id` or a `groups[].id`.

2. **Sign-in user references:** Every `signInLogs[].userId` must match a
   `users[].id`.  Sign-in logs for unknown principals are rejected.

3. **Group member references:** Every element of `groups[].members` must match
   a `users[].id`.

4. **Inherited assignment consistency:** When `roleAssignments[].assignmentType
   == "group"`, the `assignedVia` field must be non-null.  It should correspond
   to a `groups[].displayName`, though this is validated as a warning rather
   than a hard error to accommodate edge cases in real tenant exports.

5. **Timestamp well-formedness:** All timestamp fields (`assignedAt`,
   `signInTimestamp`) must be parseable as ISO 8601 UTC strings.

## Role Tier Classification

The pre-processing stage classifies each assigned role into one of three
privilege tiers.  Tier classification drives severity scoring in both
overprivilege and dormancy detection.

### Tier 0 — Global Control

Compromise of any Tier 0 role grants effective control over the entire Azure AD
tenant.  Any user holding a Tier 0 role is an immediate subject for scrutiny.

| Role Name | Role Definition ID |
|-----------|--------------------|
| Global Administrator | `62e90394-69f5-4237-9190-012177145e10` |
| Privileged Role Administrator | `fe930be7-5e62-47db-91af-98c3a49a38b1` |
| Privileged Authentication Administrator | `7be44c8a-adaf-4e2a-84d6-ab2649e08a13` |

### Tier 1 — Elevated Privilege

These roles grant broad write access to significant portions of the tenant.
Lateral movement from a Tier 1 account to Tier 0 is often feasible.

| Role Name | Role Definition ID |
|-----------|--------------------|
| User Administrator | `fe930be7-5e62-47db-91af-98c3a49a38b1` |
| Security Administrator | `194ae4cb-b126-40b2-bd5b-6091b380977d` |
| Exchange Administrator | `29232cdf-9323-42fd-ade2-1d097af3e4de` |
| SharePoint Administrator | `f28a1f50-f6e7-4571-818b-6a12f2af6b6c` |
| Compliance Administrator | `17315797-102d-40b4-93e0-432062caca18` |
| Helpdesk Administrator | `729827e3-9c14-49f7-bb1b-9608f156bbb8` |
| Application Administrator | `9b895d92-2cd3-44c7-9d02-a6ac2d5ea5c3` |
| Cloud Application Administrator | `158c047a-c907-4556-b7ef-446551a6b5f7` |
| Authentication Administrator | `c4e39bd9-1100-46d3-8c65-fb160da0071f` |

Low standalone risk.  These roles should not normally trigger findings unless

## Timestamp Format

All timestamps in the dataset must be **ISO 8601 UTC strings** in the format:

```
YYYY-MM-DDTHH:MM:SSZ
```

Examples:

```
2024-11-05T09:12:00Z   ✓  Full UTC timestamp with Z suffix
2023-06-15T09:00:00Z   ✓  Role assignment creation timestamp
2024-01-01T00:00:00Z   ✓  Midnight UTC

2024-11-05T09:12:00    ✗  Missing Z suffix (ambiguous timezone)
2024-11-05             ✗  Date-only format (not a valid timestamp here)
1699174320             ✗  Unix epoch integer (not accepted)
```

The ingestion service parses these strings into timezone-aware Python
`datetime` objects before computing derived features.

## Minimal Valid Example

This is the smallest possible dataset that will pass schema validation.
It will produce a finding for Alice (Global Admin, active account) but
no dormancy finding since she has a recent sign-in.

```json
{
  "users": [
    {
      "id": "00000000-0000-0000-0000-000000000001",
      "displayName": "Alice Johnson",
      "userPrincipalName": "alice@contoso.onmicrosoft.com",
      "userType": "Member",
      "accountEnabled": true
    }
  ],
  "roleAssignments": [
    {
      "id": "ra-00000001",
      "principalId": "00000000-0000-0000-0000-000000000001",
      "roleDefinitionId": "62e90394-69f5-4237-9190-012177145e10",
      "roleName": "Global Administrator",
      "assignmentType": "direct",
      "assignedVia": null,
      "assignedAt": "2023-06-15T09:00:00Z"
    }
  ],
  "signInLogs": [
    {
      "id": "sl-00000001",
      "userId": "00000000-0000-0000-0000-000000000001",
      "userDisplayName": "Alice Johnson",
      "signInTimestamp": "2024-10-01T08:30:00Z",
      "appDisplayName": "Microsoft Azure Management",
      "status": "Success",
      "ipAddress": "203.0.113.42"
    }
  ],
  "groups": []
}
```
